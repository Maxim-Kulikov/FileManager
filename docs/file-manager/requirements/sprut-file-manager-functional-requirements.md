## 1. Назначение

Сервис предоставляет полноценный файловый менеджер: дерево папок, редактирование содержимого, версии, поиск, массовые корректоры, восстановление и ограниченное хранение истории.

### 1.1. Основные решения

| Решение | Требование |
|---|---|
| Один логический микросервис | API и worker-процессы принадлежат одному файловому менеджеру и одной модели данных |
| PostgreSQL | Источник истины для дерева, доступа, версий, заданий и очередей |
| S3 / MinIO | Хранение неизменяемых байтов; логические пути не являются физическими ключами |
| OpenSearch | Восстанавливаемая поисковая проекция |
| Внутренние задания | PostgreSQL-очереди; Kafka для корректоров, discovery, GC и индексации не используется |
| Запуск корректоров | Без обязательного preview и подтверждения |
| Результат массовой операции | Допускаются успешные, конфликтные и неуспешные элементы одного задания |
| Конкурентные задания | Пересечение корней не является основанием для глобального запрета |
| Конфликты | Изменения одного файла защищаются CAS; default — SKIP_AND_REPORT |
| Отмена | Останавливает новые публикации, сохраняет уже выполненные изменения |
| Восстановление | Разделены откат конкретного задания и восстановление дерева на момент времени |
| История | Ограничена retention; физическая очистка учитывает живые ссылки и удержания |
| Маркеры узлов | Массив стабильных кодов в fs_node, без справочника и таблицы назначений |
| Tenant | Один tenant на развёртывание; постоянный UUID задаётся серверной YAML-конфигурацией |
| Аутентификация пользователей | Gateway проверяет Bearer token и формирует доверенный identity-контекст |
| Внутренний контекст | X-Actor-Id и X-Actor-Type принимаются только от аутентифицированных разрешённых отправителей |
| Авторизация | File Manager проверяет space и ACL независимо от проверки токена gateway |
| Инфраструктура | MinIO/OpenSearch задаются только YAML; админка создаёт space и управляет ролями/ACL |
| Файловые роли | Роль принадлежит одному space; membership назначается внешней системой по role UUID |
| Первое пространство | Создаётся вручную через MVC/REST; отсутствие spaces допустимо при запуске |
| Стек интеграций | MinIO Java SDK, OpenSearch Java client, Liquibase; SQL-доступ через jOOQ |
| Диагностика | Поддерживаются correlationId, traceId/spanId и jobId/itemId; назначения идентификаторов разделены |

### 1.2. Параметры и ограничения

Не заданы политика регистра имён, сроки хранения и квоты. Состав первой версии для dry-run, пользовательского закрепления версий и legal hold определяется отдельно.

Маркеры: TEST_CASE, REFERENCE, NEEDS_REVIEW. Произвольные пользовательские маркеры не поддерживаются.

Правила корректоров и операции восстановления не означают атомарную замену всего дерева: атомарность обеспечивается на уровне отдельного элемента и необходимых для него записей PostgreSQL.

## 2. Границы ответственности

### FR-001. Владение файловыми данными

Сервис управляет файлами, папками, версиями, ACL, upload sessions, шаблонами корректоров, заданиями изменения/восстановления, поисковой проекцией и очисткой.

Другие сервисы обращаются через контракт File Manager и не изменяют напрямую его PostgreSQL, S3-объекты или индекс.

Сохранение новой версии проходит через одну операцию File Manager и оставляет согласованные current pointer, историю, аудит и задачу индексации.

### FR-002. Интеграция с другими компонентами Sprut

Сервис предоставляет sprut-core и другим разрешённым потребителям чтение metadata, перечисление файлов и загрузку конкретных версий.

Оркестрация тестового прогона, выполнение стадий и формирование бизнес-отчёта принадлежат sprut-core. RAG получает разрешённые данные через согласованный интерфейс и не становится владельцем файлового дерева.

При длительном использовании конкретных версий потребитель должен иметь механизм удержания этих версий с определённым временем жизни и освобождением.

Rename файла сохраняет доступность чтения по fileId/versionId; запрос по current version и запрос конкретной версии имеют разные явные семантики.

### FR-003. Логические пространства

Все операции выполняются в контексте storage space и tenant. Пространство задаёт собственное дерево, физическое размещение и retention policy.

Tenant определяется конфигурацией развёртывания по FR-049. Одно развёртывание обслуживает один tenant и может содержать несколько spaces. Переключение tenant через параметры запроса не поддерживается; tenant не является идентификатором пользователя, микросервиса или S3 bucket.

Состояния пространства:

- ACTIVE: чтение и разрешённые изменения.
- READ_ONLY: чтение доступно, пользовательские изменения отклоняются.
- DISABLED: пользовательский доступ запрещён; административное обслуживание определяется отдельным разрешением.

Клиент не может выбрать произвольный bucket для обхода ограничений space. Credentials не выдаются обычным пользователям.

Пользователь одного tenant не получает metadata, содержимое, поисковые результаты или задания другого tenant через подмену идентификатора.

## 3. Файлы, папки и структура

### FR-004. Стабильные идентификаторы

Каждый файл и папка имеют стабильный nodeId. Каждый файл дополнительно имеет file_entry и currentVersionId. Версия содержимого имеет собственный versionId.

Rename и move сохраняют nodeId. Копия получает новый nodeId. Физический S3 key не зависит от пользовательского имени или положения узла.

fs_node.parent_id задаёт структуру. Дополнительный tree_path типа ltree хранится только у папок; у файлов NULL. Метки пути — стабильные UUID, от корня до самой папки. Путь синхронно поддерживается сервером и не передаётся через REST/MVC. [Правила дерева](../architecture/sprut-file-manager-tree.md).

Перемещение большой папки не требует копирования всех её S3-объектов только ради изменения пути.

### FR-005. Создание и чтение узлов

Поддерживаются создание папки, создание пустого файла или файла с загружаемым содержимым, получение metadata узла и вычисленного полного логического пути.

Пустая папка является объектом PostgreSQL и существует без S3 folder marker. У пространства один корень с tree_path=label(rootId). Создание FOLDER записывает parent.tree_path || label(nodeId), создание FILE и NEW upload finalize — NULL.

Имя не должно быть пустым, содержать разделитель пути или управляющие символы, запрещённые контрактом. Нормализация имени выполняется по одной задокументированной политике.

Две конкурентные операции создания с одинаковым нормализованным именем в одном родителе не создают два активных одноимённых узла.

### FR-006. Перечисление содержимого папки

Поддерживаются прямые дети и рекурсивное перечисление, фильтр FILE/FOLDER, ограниченный размер страницы и continuation cursor.

Контракт задаёт порядок выдачи и семантику изменения дерева между страницами. Для фонового discovery используется keyset по стабильному ID, а не сортировка по изменяемому имени.

Обычный список не гарантирует глобальный неизменяемый snapshot дерева. Допустимые дубли и пропуски при конкурентных изменениях определяются контрактом; point-in-time snapshot требует отдельного механизма.

Перечисление большого дерева возобновляется по cursor и не требует загрузить все пути в память сервера.

Текущие потомки выбираются без Recursive CTE: FOLDER по tree_path <@ root.tree_path, FILE через JOIN на путь родительской папки. Состояние всех предков и ACL проверяются отдельно. Обычный порядок — FOLDER first/name/id, recursive — id. pageSize ограничивает выдачу, но не число кандидатов или стоимость сортировки; применяются DB timeout и ограниченные ресурсы.

### FR-007. Потоковое перечисление

Сервис предоставляет поток metadata файлов внутри выбранной папки с настройкой recursive и фильтрами.

Формат — NDJSON: одна запись на строку. Это поток описаний файлов, а не перемешанных байтов всех файлов.

Поток должен поддерживать ограниченную буферизацию, остановку при disconnect и документированный способ возобновления. Для возобновления можно использовать отдельный paginated API; возобновление того же HTTP-потока после обрыва не гарантируется.

Первые записи приходят до завершения обхода; медленный клиент не вызывает накопление всего результата в RAM.

### FR-008. Rename и move

Операции rename/move принимают ожидаемую revision. Move проверяет целевого родителя, доступ, пространство, коллизии имён и отсутствие циклов.

Перемещение в своё поддерево запрещено. Конкурентные move не должны обходить проверку циклов. Move между spaces в первой версии отклоняется; copy в другой space — отдельное открытое решение.

Изменение namespace создаёт node_revision, audit и задачу переиндексации. Rename/move папки требует актуализации путей её потомков в поиске.

Rename сохраняет tree_path. Move FILE меняет parent_id при tree_path=NULL. Move FOLDER под exclusive space lock атомарно меняет parent_id источника и prefix всех текущих вложенных папок, включая TRASHED/PURGING. Промежуточный COMMIT и последующая фоновая достройка tree_path запрещены. Производный rewrite потомков не меняет их revision/updated_at и не создаёт node_revision.

Preflight вне изменяющей TX считает папки и проверяет depth/path limits; generation сверяется после блокировки space. Число изменяемых папок ограничено maxAtomicMoveFolders из YAML/capabilities. Превышение возвращает 413 RESOURCE_LIMIT_EXCEEDED без изменений. Rename без смены parent не переписывает пути и не расходует этот лимит.

- Два конфликтующих rename не приводят к потере одного из изменений.
- Одновременные A → B и B → A не создают цикл.
- После move чтение по nodeId работает, а старый путь больше не разрешается в прежний узел.

### FR-009. Копирование

Поддерживаются копирование файла и копирование поддерева с явной политикой коллизий. По умолчанию коллизия отклоняется, без автоматической перезаписи.

Копия получает новые nodeId и историю, относящуюся к копии. В пределах допустимой границы хранения она может переиспользовать immutable content_object.

Путь новой папки вычисляется из актуального родителя назначения и нового ID в TX публикации. tree_path источника не копируется; файлы создаются с NULL. Родители публикуются до дочерних COPY_NODE.

Копирование большого дерева выполняется как возобновляемая фоновая операция с прогрессом и поэлементными результатами.

Удаление оригинала и GC его версий не удаляют объект, который ещё используется копией.

Примечание к модели: асинхронная копия дерева пока не представлена отдельным job_type в текущей PUML. Перед реализацией необходимо дополнить очередь, не маскируя COPY под CORRECTOR.

### FR-010. Корзина и удаление

Пользовательское удаление переводит узел в корзину. Удалённая папка скрывает всё своё поддерево в обычных списках, поиске и прямом доступе независимо от способа физической разметки потомков.

Поддерживаются просмотр корзины и восстановление в исходную или выбранную разрешённую папку с проверкой коллизий.

Физическое удаление выполняется только по правилам retention/GC. Повторная команда удаления имеет предсказуемый идемпотентный результат.

Прямой запрос потомка папки в корзине не позволяет обходить состояние удалённого предка.

## 4. Содержимое и версии

### FR-011. Загрузка файлов

Поддерживаются upload session, потоковая загрузка, multipart для больших файлов, завершение загрузки и abort.

Создание upload session фиксирует space, цель, предполагаемое имя, автора и срок жизни. Для обновления фиксируются baseVersionId и ожидаемая contentRevision.

Размер/checksum проверяются перед публикацией. Для нового файла конфликт имени разрешается при finalize, а не только при создании сессии.

Незавершённая или повреждённая загрузка не становится current version.

### FR-012. Finalize загрузки

После проверки объекта сервис атомарно публикует file_version, переключает currentVersionId, записывает node_revision/audit и создаёт search_index_task.

Повторный finalize возвращает ранее полученный результат. При конфликте исходной версии чужие байты не перезаписываются; подготовленный объект остаётся кандидатом на безопасную очистку.

Состояния upload: INITIATED, UPLOADING, VERIFYING, COMPLETED, ABORTED, EXPIRED, FAILED.

Падение после успешного S3 upload и до DB commit не создаёт видимый файл без metadata и не требует повторно публиковать две версии.

### FR-013. Чтение и скачивание

Поддерживаются чтение current version и конкретного versionId, потоковая отдача содержимого, metadata размера/checksum/MIME и HTTP Range.

Версия должна принадлежать запрошенному файлу и space. Авторизация выполняется до отдачи байтов.

Загрузка новой версии во время скачивания не меняет байты уже выбранной версии в середине ответа.

### FR-014. Временные ссылки и ZIP

Сервис может выдавать ограниченные по времени presigned-ссылки после авторизации. Ссылка ограничена конкретным объектом и операцией; секреты S3 не раскрываются.

Сервис поддерживает скачивание папки как ZIP. Контракт задаёт, какие версии попадают в архив и как сообщаются ошибки чтения.

Архив собирается по manifest конкретных versionId, чтобы переименования и обновления не меняли уже выбранные элементы. Объекты удерживаются на время подготовки/выдачи.

Большой ZIP может готовиться асинхронно. Ошибка после начала потокового ZIP не должна маскироваться под успешно полный архив.

Немедленный отзыв уже выданной presigned-ссылки не гарантируется. Время доступа ограничивается TTL ссылки.

### FR-015. Редактирование и история версий

Каждое изменение содержимого создаёт новую immutable file_version и при необходимости новый content_object.

API истории возвращает доступные версии, автора, время, origin, размер и сведения о restore. Уже очищенная версия не выдаётся как доступная для скачивания.

Публикация версии защищена ожидаемым versionId/contentRevision. Номера версий монотонны и не переиспользуются после GC.

Параллельные сохранения одного файла дают успешное сохранение и явный конфликт, а не молчаливую потерю данных.

### FR-016. Восстановление одной версии

Пользователь может сделать доступную историческую версию текущей. Операция создаёт новую версию с provenance исходной версии.

При наличии объекта разрешено переиспользовать его байты. Последующие версии не удаляются.

После V1 → V2 → restore V1 видна новая V3, а доступные V1/V2 остаются в истории до retention.

## 5. Универсальный поиск и выбор файлов

### FR-017. Поиск имён и содержимого

Поддерживаются поиск файлов/папок по имени и логическому пути, поиск по тексту поддерживаемых форматов, ограничение по roots, типу узла и другим согласованным фильтрам.

Сервис сообщает ограничения поддерживаемых кодировок, типов, размера извлекаемого текста и поисковой выдачи. Отсутствие извлечённого текста не означает отсутствие файла.

Поиск eventual consistent. Найденные ID проходят актуальную проверку существования, состояния и доступа через File Manager.

Устаревший индекс не раскрывает содержимое или snippet файла после отзыва READ.

### FR-018. Поиск папок по наличию файла

Поддерживается запрос: получить полные логические пути папок, непосредственно содержащих файл с заданным именем.

Отдельно задаётся, требуется ли непосредственное наличие файла или наличие в любом потомке. Для одного результата папки исключаются дубли.

Пример назначения: найти тестовые папки, содержащие callsequence; конкретное имя/расширение задаётся запросом, без фиксированного значения в API.

При непосредственном режиме файл в /a/b не приводит к выдаче /a только потому, что /b является его потомком.

### FR-019. Выбор файлов внутри заданных корней

Поддерживается запрос файлов с заданным именем/шаблоном внутри одного или нескольких roots с exclusions и recursive.

Пересекающиеся roots нормализуются. Сравнение путей учитывает границы сегментов: /a не означает /ab.

Для операций изменения кандидаты и актуальные версии проверяются в PostgreSQL; OpenSearch может помогать поиску, но его неполнота не должна определять полный manifest массового задания.

Файл в пересечении двух roots обрабатывается одним item, а файл под EXCLUDE не изменяется.

### FR-020. Управление поисковой проекцией

Изменения создают задачи индексации в PostgreSQL. Поддерживаются повтор обработки ошибок, переиндексация поддерева и полный rebuild.

Документ основного индекса соответствует nodeId и текущей версии. Исторические версии в основной индекс не добавляются.

При обновлении/удалении учитывается searchRevision. Поздний результат старого worker не должен восстанавливать удалённый документ или заменять свежий текст.

После восстановления OpenSearch накопленная очередь сходится к текущему состоянию PostgreSQL.

## 6. Шаблоны корректоров и выражения

### FR-021. Управление шаблонами

Поддерживаются создание, чтение, изменение и архивирование шаблона. Редактирование создаёт immutable corrector_rule_version.

Версия содержит тип корректора, definition, hash и engineVersion. Архивирование шаблона не изменяет уже запущенный job.

Редактирование шаблона во время обработки миллиона файлов не меняет правила оставшихся items текущего задания.

### FR-022. Текстовые корректоры

Поддерживаются текстовая замена и regex-замена, case sensitivity и режим одной/всех замен.

Фильтры покрывают S3_KEY как legacy-вход, PREFIX, PREFIX_PART, FILENAME, FILENAME_PART и EXTENSION. В целевой модели основными являются logical path/node metadata, а не физический object_key.

Операторы: STARTS_WITH, CONTAINS, ENDS_WITH, EQUALS и MATCHES_REGEX. Для составных условий definition явно задаёт AND/OR и порядок действий.

- Replacement с группами работает по документированным правилам.
- Файл без совпадений получает UNCHANGED, без новой версии и задачи переиндексации.
- Кодировка результата и допустимое поведение для бинарного/невалидного текста определены.

### FR-023. Структурные JSON-корректоры

Поддерживается TEST_JSON: выбор объектов по согласованным source/call/stage-фильтрам, вставка, редактирование, удаление и замена полей/структур.

Правила валидируются до запуска; содержимое — перед публикацией результата. Неизвестные пути и неправильный JSON получают явный результат согласно настройке правила.

Атомарность нескольких файлов одной тестовой папки не гарантируется. Совместная публикация файлов требует отдельного бизнес-требования и механизма реализации.

Ошибка JSON одного файла не отменяет успешно обработанные независимые файлы и не публикует повреждённый результат.

### FR-024. Параметризация и кастомные выражения

Поддерживается PARAMETRIZATION с текущими сценариями DATE и CUSTOMER_REQUEST_EXT_ID и возможностью зарегистрировать дополнительные безопасные выражения/plugins.

Значения, зависящие от времени, timezone, seed или генерации ID, фиксируются в command/item snapshot так, чтобы retry одного item воспроизводил тот же результат.

Пользовательское выражение не получает произвольный доступ к Java runtime, сети, ОС, credentials или другим tenant.

Повтор item на следующий день не изменяет подставленную дату/ID только из-за времени retry.

## 7. Массовые задания и очередь

### FR-025. Запуск без подтверждения

Команда запуска принимает конкретные правила/параметры, ROOT и EXCLUDE. После проверки доступа и конфигурации создаётся durable job.

Ответ 202 выдаётся после commit PostgreSQL с job и необходимыми для запуска данными. В ответе — jobId и адрес/способ получения состояния.

Полный preview, просмотр diff и ручное подтверждение не являются обязательной стадией. Dry-run — отдельный режим без публикации изменений.

После 202 и немедленного падения API job существует и доступен для продолжения worker.

### FR-026. Фиксация команды

Job сохраняет полный command snapshot и hash: правила, параметры, engineVersion, roots/exclusions, инициатора и необходимый контекст вычисления.

Повтор обработки не зависит от текущего изменяемого шаблона или локального cache конкретной реплики.

Перезапуск worker и удаление/архивирование шаблона не меняют семантику уже принятой команды.

### FR-027. Постраничный discovery

Discovery обходит выбранное дерево страницами и сохраняет подходящие items и checkpoint в одной транзакции.

Состав задания накапливается постепенно; обработка уже обнаруженных items может идти до завершения discovery.

Для файла фиксируются nodeId, baseVersionId и contentRevision. Для структурных операций также фиксируется nodeRevision. Нужные версии удерживаются атомарно с созданием item.

Обычный корректор имеет пофайловый snapshot в момент обнаружения. Файлы, созданные/перемещённые во время обхода, могут не попасть в этот job; полный снимок дерева на момент старта не гарантируется.

Crash после сохранения страницы и retry discovery не создают двойную обработку файла.

### FR-028. Выполнение и retry

Worker резервирует item в PostgreSQL на ограниченный lease с увеличением leaseToken. Длительное чтение/transform/upload выполняются вне DB-транзакции.

Retry различает временную ошибку, постоянную ошибку входа, конфликт и отмену. Исчерпание попыток переводит item в FAILED.

Истечение lease позволяет передать item другой реплике. Старый worker не может выполнить commit после утраты lease/token.

Два worker могут физически выполнить вычисление при сбое lease, но публикуется не более одного результата соответствующего item.

### FR-029. Независимые файлы и конфликты

Разные файлы/папки могут изменяться параллельно. Пересечение roots само по себе не блокирует запуск.

Default conflict policy — SKIP_AND_REPORT. Публикация сверяет текущую версию/contentRevision с базовой; структурная операция сверяет необходимую nodeRevision и инварианты родителей.

Конфликт не приводит к автоматическому merge, overwrite или повторному применению неидемпотентного корректора к новой версии.

Два job на пересекающихся roots успешно обрабатывают непересекающиеся файлы; на одном файле конфликт явно отражается в результате.

### FR-030. Поэлементная атомарность

Для успешного item атомарно фиксируются переключение версии/состояния, история, resultVersion/resultRevision, итог item, аудит и задача индексации.

Ни успешный статус без опубликованного результата, ни опубликованный результат с потерянным статусом не допустимы.

Crash в любой точке DB-транзакции оставляет либо исходное состояние, либо полный результат.

### FR-031. История и прогресс

API предоставляет список job, фильтры, детали, инициатора, тип, время, roots/exclusions, сведения о конфигурации и результаты items.

Статистика различает scanned nodes, найденные items, SUCCEEDED, UNCHANGED, CONFLICT, FAILED и CANCELLED. Во время discovery итоговое количество ещё неизвестно и может увеличиваться.

Logical processedBytes не должны повторно увеличиваться при retry; фактический повторный I/O учитывается отдельно в telemetry.

Подробный список результатов выдаётся страницами. Ошибки доступны с безопасным errorCode/message.

Сумма терминальных исходов равна количеству терминальных уникальных items, а не количеству доставок/попыток.

### FR-032. Завершение и частичный результат

Job завершает обработку после окончания discovery и перехода всех относящихся items в терминальные состояния.

Повторная финализация не создаёт второй итог. Кэш progress не является источником решения о завершении.

Семантика:

- COMPLETED: discovery завершён; все items SUCCEEDED или UNCHANGED.
- COMPLETED_WITH_ERRORS: discovery завершён; имеются FAILED/CONFLICT или другие неуспешные элементы.
- CANCELLED: принят cancel; успешные изменения могли сохраниться.
- FAILED: задание не смогло корректно продолжить discovery/оркестрацию; часть изменений также могла сохраниться.

Пустой manifest допустим и завершается с нулевым результатом. FAILED не означает автоматический откат.

Параллельное завершение последних items приводит к одному устойчивому итоговому состоянию.

### FR-033. Отмена на лету

Cancel фиксирует CANCEL_REQUESTED. Повторный cancel идемпотентен; терминальный job возвращает текущее состояние.

После commit CANCEL_REQUESTED новые изменения задания не публикуются. Discovery прекращается; невыполненные items становятся CANCELLED; активные workers прекращают работу в безопасных точках или теряют право на commit.

Уже опубликованные изменения сохраняются. Остановка CPU-работы/передачи байтов может занять время; это не разрешает поздний commit.

Гонка cancel с worker commit имеет определённый порядок — либо commit завершился раньше cancel, либо публикация отклонена.

### FR-034. Повтор неуспешных элементов

Пользователь может инициировать повтор только выбранных FAILED/CONFLICT элементов завершённого job.

Повтор создаёт новый job со ссылкой на исходный, новой авторизацией и явно выбранной актуальной базой. Старый итог не переписывается.

CONFLICT не повторяется автоматически без повторного выбора версии. Items со статусом SUCCEEDED/UNCHANGED исходного job исключаются из повторной обработки.

Retry failed subset не повторяет уже выполненную неидемпотентную замену на остальных файлах.

Примечание: связь retry-parent и политика rebasing требуют уточнения модели/контракта; source_job_id сейчас документирован для JOB_ROLLBACK.

## 8. Откат задания и восстановление дерева

### FR-035. Откат конкретного job

JOB_ROLLBACK создаёт новое задание компенсации по успешно изменённым items исходного задания.

Для файла допустима компенсация, только если currentVersion соответствует результату исходного item; для структурных операций проверяется ожидаемое состояние/revision.

Содержимое до корректора становится новой версией. Чужое последующее изменение даёт ROLLBACK_CONFLICT.

UNCHANGED не требует компенсации. Нужные исходные items/версии должны быть доступны; запуск атомарно проверяет срок rollback и продлевает/переносит holds.

После изменения файла пользователем rollback корректора сохраняет это изменение и фиксирует конфликт.

### FR-036. Восстановление дерева на T

TREE_RESTORE принимает выбранные roots и timestamp с явным timezone. Используется история namespace и версий, а не удаление S3-версий новее даты.

tree_path не входит в node_revision: историческая структура на T строится по parent_node_id на T. При публикации restore/структурного rollback текущий путь вычисляется из актуального восстанавливаемого parent. Перенос существующей папки обновляет prefix всех её текущих вложенных папок в той же TX и ограничен maxAtomicMoveFolders. Превышение завершает item как FAILED/RESOURCE_LIMIT_EXCEEDED без частичной смены prefix.

Учитываются содержимое, существование узлов, имена, родители, маркеры и состояние корзины на T. Объекты, созданные после T, убираются из активного восстанавливаемого дерева по безопасной политике.

Выбранный root задаётся стабильным ID. Состав на T и актуальный состав рассматриваются вместе; move за границу scope и коллизия имени могут дать CONFLICT и не должны неявно затрагивать чужое дерево.

ACL/права доступа по умолчанию не возвращаются к историческому состоянию. Выполняющий restore пользователь сохраняет обязанности текущей авторизации.

- Восстанавливаются переименованные, перемещённые и удалённые после T узлы, если необходимая история доступна.
- Временные версии после T остаются доступными до retention.
- Частично выполненный restore не отображается как атомарно восстановленный snapshot всего дерева.

### FR-037. Планирование восстановления

Restore проверяет доступность T и создаёт tree_history_hold атомарно с job. История на T не должна исчезнуть, пока job строит manifest.

Родители восстанавливаются до детей; удаления зависимых узлов упорядочиваются безопасно. Ошибка prerequisite переводит dependent item в явный терминальный результат.

GC, начавшийся во время длительного планирования restore, не удаляет необходимые базовые состояния/байты.

### FR-038. Доступность восстановления

API показывает restoreAvailableFrom для space и rollbackAvailableUntil для job.

Запрос за пределами гарантированного окна отклоняется с понятной причиной. Наличие отдельных старых версий не означает доступность полного восстановления дерева на любую старую дату.

Истёкший rollback не запускается и не завершается позже непредсказуемым отсутствием половины базовых версий.

## 9. Retention и очистка

### FR-039. Политика хранения

Поддерживаются настройки сроков версий, минимального числа версий файла, окна restore, корзины, rollback, деталей/summary job, audit, GC grace и orphan grace.

Политики задаются для space в границах tenant. Конкретные численные defaults ещё не утверждены.

Сокращение retention согласованно меняет обещанную доступность восстановления и eligibility для GC. Уже активные операции и holds сохраняют приоритет.

Изменение политики не удаляет current version или версию, удерживаемую выполняющимся job.

### FR-040. Условия сохранения версии

Версия сохраняется при наличии хотя бы одного защищающего условия:

- Текущий указатель файла.
- Попадание в срок/минимальное количество retained versions.
- Использование retained node_revision, включая граничное состояние окна restore.
- Активный version_hold/tree_history_hold.
- Использование незавершённым upload/item/export или разрешённым внешним потребителем.

Типы удержания: USER_PIN, SHARE и LEGAL_HOLD. Состав UI и административных операций определяется отдельно.

Версия, созданная год назад, остаётся доступной, если она является текущей или нужна состоянию внутри гарантированного окна restore.

### FR-041. Поэтапный GC

Очистка разделяет истечение доступности версии и удаление физического объекта. После RETIRED версия запрещена для новых удержаний/использований.

Общий content_object удаляется только при отсутствии всех защищающих ссылок. GC_PENDING запрещает новые ссылки.

Удаление выполняется durable gc_task после grace. NotFound считается успехом. Metadata удаляется после подтверждения удаления объекта либо безопасного сохранения объекта через другие версии.

Retry GC после удаления S3 и падения до DB commit заканчивается корректно.

### FR-042. Очистка metadata и поисковых данных

Поддерживаются пакетная очистка истёкших деталей job/items/cursors, upload sessions, retired versions, released holds, выполненных queue tasks и idempotency records.

Удаление не блокируется бессрочно случайными FK. Необходимые references освобождаются после завершения и retention владельца.

В OpenSearch хранятся текущие документы и необходимые tombstones. Истёкшие legacy history documents, если они существовали, удаляются адресными задачами.

Текущий документ не удаляется только потому, что очищается старая версия того же файла. Tombstones физически удаляются после исключения старых writers/retries либо при безопасной смене поколения индекса.

Очистка истории уменьшает S3/DB/legacy index, сохраняя поиск по актуальной версии.

### FR-043. Reconciliation и orphan cleanup

Обслуживание выявляет зависшие leases/jobs, истёкшие uploads, незавершённые multipart, неиспользуемые reserved objects, потерянные/ошибочные задачи индексации и ошибки GC.

Orphan sweep ограничен принадлежащим space префиксом и grace; перед удалением повторно проверяется отсутствие живой ссылки/сессии.

Отсутствующий объект, на который всё ещё ссылается доступная версия, считается инцидентом целостности, а не нормальной очисткой.

Свежий upload не удаляется sweep только потому, что metadata finalize ещё не завершён.

## 10. Доступ, аудит и контракт API

### FR-044. Авторизация

Все пользовательские API требуют подтверждённого пользователя/сервиса и проверяют tenant, space и эффективные права.

Пользовательский Bearer token проверяется gateway. File Manager получает actor-контекст по FR-050, аутентифицирует внутреннего отправителя и выполняет собственную авторизацию. Наличие identity-заголовков само по себе не подтверждает полномочия. Tenant берётся только из серверной конфигурации.

Для READ, WRITE, DELETE, SHARE и ADMIN используются bitmask flags и наследование SELF/CHILDREN/SUBTREE. Политика доступа — default deny и объединение действующих разрешающих grants.

Move проверяет источник и назначение; массовое изменение повторно проверяет WRITE непосредственно перед commit. Изменение ACL во время job не даёт worker права продолжать неразрешённые изменения.

Если пользователь видит файл, но не может менять его, item может получить явную ошибку доступа. Невидимые пользователю узлы не раскрываются через пути, ошибки или progress.

Job, начатый до отзыва WRITE, не публикует новые изменения после вступления отзыва в силу.

### FR-045. Аудит

Сервис фиксирует инициатора, время, operation/item IDs и значимые before/after metadata для изменения namespace, версии, ACL, restore и purge.

Для связи операции с диагностикой фиксируются correlationId и, при наличии, traceId/spanId. Инициатор USER/SERVICE и аутентифицированный вызывающий сервис различаются; фоновая обработка сохраняет исходного инициатора и отдельно фиксирует исполнителя. Технические токены и полный набор HTTP-заголовков в audit не сохраняются.

История аудита не содержит байтов файлов, credentials или полного дерева в каждой записи. Очистка рабочих таблиц не уничтожает audit раньше его retention.

Опубликованную версию можно связать с пользователем, upload или конкретным item корректирующего задания.

### FR-046. Идемпотентность команд

Для создания upload/job и других повторяемых команд поддерживается Idempotency-Key в scope configured tenant/actorType/actorId/operation/resource. Caller identity дополнительно учитывается, если влияет на семантику команды или доступ.

Повтор того же key и payload возвращает прежний ресурс/результат; другой payload с тем же key даёт конфликт.

Конкурентные запросы с одним key не создают несколько job. Срок жизни key и поведение после истечения retention документируются.

Потеря HTTP-ответа и повтор команды не запускают второй корректор.

### FR-047. Ошибки и квоты

API различает ошибки валидации, доступа, конфликта, истёкшей версии/restore point, превышения лимита и временной недоступности зависимости.

Ошибки имеют стабильный machine-readable code и correlationId; пользовательский текст не подменяет код.

correlationId возвращается также в X-Correlation-Id; при наличии контекста трассировки ошибка может включать traceId. Диагностические ID не используются как подтверждение доступа, ключ идемпотентности или идентификатор результата задания.

Поддерживается проверка настроенных квот space/tenant и ограничений job. При достижении лимита discovery не зависает бессрочно и не сообщает ложный успешный результат.

Limit exceeded во время discovery приводит к устойчивому результату с объяснением и сохранением уже выполненных items.

### FR-048. Маркеры файлов и папок

Каждый FILE/FOLDER хранит `markers` непосредственно в `fs_node` как `TEXT[] NOT NULL DEFAULT '{}'::text[]`. Новые таблицы `marker`/`node_marker` не создаются. API возвращает массив кодов для каждого элемента в metadata, списках, потоке и поисковых результатах; отсутствие маркеров представляется `[]`, не `null`.

Коды маркеров:

| Код | Визуальный смысл |
|---|---|
| TEST_CASE | Элемент, связанный с тестовым кейсом |
| REFERENCE | Эталонный элемент |
| NEEDS_REVIEW | Элемент, требующий внимания |

Коды стабильны и не зависят от имени/пути узла. Фронт сопоставляет код с иконкой, цветом и бейджем; неизвестный клиенту код игнорируется при выборе оформления; отображение узла сохраняется. Маркеры не предоставляют права доступа и не заменяют node_type, ACL, статус узла или динамические статусы прогонов.

`PATCH /api/v1/nodes/{nodeId}/markers` с `If-Match` заменяет весь набор: `{"markers":["REFERENCE","NEEDS_REVIEW"]}`. `{"markers":[]}` снимает все маркеры. Отсутствующий/null массив, неизвестные коды и null элементы отклоняются. Дубли нормализуются; порядок не несёт бизнес-смысла, хранение/выдача используют стабильную сортировку кодов. Возвращается metadata узла с новой revision. Проверяются текущий tenant/space, WRITE и доступность узла для изменения; READ_ONLY/DISABLED запрещают изменение.

Реальное изменение выполняется в одной PostgreSQL-транзакции: CAS `revision`, обновление `updated_at`, закрытие/создание `node_revision` со снимком маркеров, увеличение `search_revision`, NODE-задача индексации и аудит с прежним/новым набором. Несовпавшая revision даёт конфликт без частичного обновления. При совпавшей revision повтор того же набора является no-op: новая история/задача не создаётся.

Маркеры назначаются только выбранному узлу, без наследования и неявного рекурсивного обновления потомков. Rename/move/trash/восстановление из корзины сохраняют назначения. Copy переносит набор маркеров на новый узел. Корректоры и восстановление отдельной версии содержимого не изменяют markers. TREE_RESTORE возвращает снимок markers на T через новую node_revision; обычные ограничения конфликтов и retention сохраняются.

Смена markers не создаёт file_version/content_object, не изменяет content_revision и не выполняет S3 upload. Новая node_revision повторно ссылается на прежнюю версию содержимого. История маркеров очищается вместе с обычной историей узла; отдельного бесконечного журнала нет.

OpenSearch содержит текущую проекцию markers и обновляется через существующую PostgreSQL-очередь. В ответах поиска массив берётся из актуального fs_node вместе с проверкой доступа, а не из потенциально устаревшего документа. Отдельные JOIN или запрос на маркеры для каждого элемента не нужны.

- Новые файлы/папки возвращают `markers: []`; списки и поток всегда включают поле.
- Назначение/снятие, дубли, неизвестные коды и отсутствие WRITE проверены.
- Два изменения с одной revision не теряют назначения: один commit, другой конфликт; rename против смены markers также защищён CAS.
- Повтор того же набора с актуальной revision не раздувает историю, индексную очередь или S3.
- TREE_RESTORE восстанавливает исторические маркеры; восстановление только содержимого оставляет текущие маркеры.
- При недоступном OpenSearch metadata/list продолжают возвращать актуальные markers; индекс догоняет после восстановления.

### FR-049. Tenant из конфигурации развёртывания

Обязательная настройка задаётся в application YAML:

```yaml
sprut:
  file-manager:
    tenant-id: ${SPRUT_TENANT_ID}
```

Значение является постоянным UUID. Все API и worker-реплики одного развёртывания используют одинаковый tenantId. Генерация значения при старте и значение по умолчанию запрещены. Отсутствующее, неразрешённое или некорректное значение препятствует запуску по NFR-042.

При создании storage_space сохраняется настроенный tenantId. При чтении или изменении существующего space, а также при выполнении фонового задания, проверяется принадлежность настроенному tenant. Ресурсы другого tenant не раскрываются. Входные body/query/headers и claims пользовательского токена не изменяют эффективный tenantId.

Изменение tenantId требует отдельной процедуры миграции принадлежности данных и проверки ссылок, ACL, очередей, S3 namespace и поисковой проекции. Изменение конфигурации не выполняет автоматическое переназначение данных. Наличие общих технических хранилищ не предоставляет доступ к данным соседнего tenant.

Отсутствующая настройка запрещает запуск; несколько replicas работают с одним UUID; запросы и задания не получают доступ к space другого tenant; подмена tenant в запросе не меняет эффективный контекст.

### FR-050. Доверенный identity-контекст внутренних запросов

Для пользовательских обращений gateway проверяет подпись токена, срок действия, issuer и audience. До маршрутизации gateway удаляет все входящие X-Actor-* и формирует новые значения из проверенной identity. Добавление второго значения к клиентскому заголовку запрещено.

Внутренний контракт использует:

| Заголовок | Значение |
|---|---|
| X-Actor-Id | Стабильный UUID пользователя либо сервисного principal |
| X-Actor-Type | USER или SERVICE |
| X-Actor-Roles | Подтверждённые UUID локальных ролей; один comma-separated header, максимум 128 |
| X-Actor-Groups | Подтверждённые UUID внешних групп для прямых GROUP grants; максимум 128 |
| X-Correlation-Id | Диагностический идентификатор по FR-051; не является identity |

Caller определяется аутентификацией внутреннего соединения, а не произвольным заголовком. File Manager доверяет actor-контексту только для разрешённых сочетаний caller и режима работы по NFR-043. Пользовательский Bearer token не требуется в контракте File Manager; его передача не заменяет проверку caller и identity-заголовков.

Прямой системный вызов sprut-core выполняется от SERVICE principal с собственными ACL. X-Actor-Id сервисного principal сопоставляется с аутентифицированным caller по серверной конфигурации. Вызов от имени пользователя разрешён только gateway либо явно разрешённому делегирующему сервису с проверяемым механизмом делегирования. Самостоятельное указание чужого USER ID не предоставляет доступ.

Отсутствующий или недействительный caller отклоняется на транспортном уровне либо HTTP 401; аутентифицированный, но неразрешённый caller — HTTP 403. Отсутствующие, некорректные, дублирующиеся или содержащие несколько значений actor-заголовки от доверенного caller — HTTP 400. Заголовки HTTP обрабатываются без учёта регистра. UUID и enum проходят строгую валидацию; идентификаторы и полномочия из body не используются как альтернативный источник identity.

File Manager самостоятельно проверяет space, видимость ancestors и права READ/WRITE/DELETE/SHARE/ADMIN. Переданные gateway роли не заменяют ACL: локальная ACTIVE роль должна иметь node binding, а права берутся из текущего role_permission. При создании job сохраняется actor-контекст, необходимый для последующей проверки прав; пользовательский токен не сохраняется. Worker перед публикацией проверяет действующие права инициатора. Транспортная identity worker не предоставляет инициатору дополнительные права.

Клиентские X-Actor-* не проходят gateway без замены; прямой вызов недоверенного сервиса отклоняется; SERVICE не может подменить USER; отзыв WRITE после запуска job блокирует новые публикации.

### FR-051. Correlation и трассировочный контекст

Сервис поддерживает X-Correlation-Id независимо от traceId/spanId. Интеграция может передать correlationId для связи нескольких запросов и систем; этот ID не обязан совпадать с traceId.

Начальный формат: 1..128 ASCII-символов, соответствующих `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`. Значение не содержит секретов или персональных данных. При отсутствии заголовка gateway генерирует UUID; для разрешённого прямого вызова генерацию выполняет File Manager. Допустимое значение сохраняется без замены. Некорректное, пустое или многозначное значение отклоняется HTTP 400; для диагностики такого отказа генерируется новый безопасный ID.

Принятый либо сгенерированный correlationId возвращается в X-Correlation-Id, включая ответы на ошибки, сформированные приложением. Ошибки содержат то же значение в body. Отказы до входа в приложение, в том числе TLS handshake failures, не имеют этой гарантии. Каждый последующий запрос, включая polling и cancel, имеет собственный запросный контекст; отсутствие ID в новом запросе не означает повторное использование ID создания job.

Назначения идентификаторов:

| Идентификатор | Назначение |
|---|---|
| correlationId | Связь запросов и операций по договорённости интеграции |
| traceId | Связь spans одной распределённой трассировки |
| spanId | Конкретная операция внутри трассировки |
| jobId / itemId | Постоянная бизнес-связь задания и элемента, включая retries и перезапуски |
| Idempotency-Key | Защита повторяемой команды от повторного создания результата |

HTTP propagation выполняется настроенной библиотекой только для поддерживаемых клиентов и механизмов переноса контекста. Передача tracing headers не означает автоматической передачи X-Correlation-Id; для него требуется отдельная настройка propagation. Отсутствие или некорректность трассировочного контекста приводит к созданию новой трассировки согласно политике инструментации и не заменяет correlationId.

При принятии job correlationId исходной команды и разрешённый трассировочный контекст сохраняются durable в PostgreSQL атомарно с job. Состав сохраняемого контекста ограничен whitelist; Authorization, произвольные headers и непроверенный baggage не сохраняются. Worker восстанавливает correlationId и создаёт контекст обработки каждой попытки по NFR-036. Один job может иметь несколько traces, связанных через jobId/itemId и correlationId исходной команды.

Polling, cancel и retry-запросы не переписывают correlationId исходного job; их запросный контекст фиксируется отдельно. Новый retry/rollback job сохраняет ID своей команды и ссылку на source job; связь с исходной операцией не зависит от совпадения correlationId. Повтор POST с тем же Idempotency-Key и другим correlationId не создаёт новое задание.

Принятый ID сохраняется в ответе и downstream-вызовах; отсутствующий ID генерируется; некорректный отклоняется без включения исходного значения в логи; crash/retry worker сохраняет диагностическую связь job; correlationId не влияет на ACL и идемпотентность.

### FR-052. Подключения только из YAML

MinIO/OpenSearch имеют по одной общей конфигурации из YAML: endpoint(s), region/bucket/base-prefix, index-alias, TLS и limits. Credentials доставляются извне. Пространства не выбирают подключение; таблицы управляемых подключений нет.

API каталога подключений отсутствует. Все spaces используют общий bucket с prefix base/spaces/spaceId/ и общий индекс с tenantId/spaceId. Поля выбора инфраструктуры запрещены в REST/MVC.

Сервис проверяет общую YAML-конфигурацию, TLS и сетевые назначения. Startup сверяет fingerprints общих targets с размещением spaces, исключая credentials/timeouts. Переезд требует migration/rebuild/cutover и fencing, не автоматического переназначения данных. Секреты не копируются в PostgreSQL/audit/logs.

Ротация credentials применяется согласованным rollout. Replicas не допускаются к операциям при несовпадении binding; transient OpenSearch outage не означает повреждение конфигурации и допускает деградацию поиска.

CRUD подключений отсутствует; неподдерживаемый key/type отвергается; изменение credentials не меняет размещение; несовместимый binding не допускает writers; ни один API/HTML не возвращает secrets.

### FR-053. Каталог ролей и файловые bindings

File Manager хранит access_role, role_permission и node_acl bindings. Роль принадлежит одному space, имеет постоянный UUID, имя, revision и статус ACTIVE/ARCHIVED. Приложение поддерживает фиксированные READ/WRITE/DELETE/SHARE/ADMIN. ADMIN — существующий файловый код scoped административных действий; он не является platform administrator и не включает READ/WRITE автоматически. Термин «управление доступом» не вводит второй неэквивалентный permission code. Произвольные действия через форму не создаются.

Внешняя identity-система читает разрешённый каталог ролей и назначает UUID пользователю/сервису. Локальные user-role memberships, пароли и копия пользовательского каталога не создаются. X-Actor-Roles принимается только от разрешённого caller с согласованным issuer/delegation protocol. Неизвестные и ARCHIVED роли не дают доступа. Роль без node_acl binding не разрешает файловые операции.

USER/GROUP/SERVICE UUID принадлежат единому каноническому namespace развёртывания. Если внешние issuer используют другие идентификаторы, gateway/identity adapter сопоставляет их с каноническими UUID; произвольный sub не преобразуется в UUID без согласованного mapping. Прямые grants и job initiator используют тот же namespace.

node_acl поддерживает ROLE наряду с прямыми USER/GROUP/SERVICE grants. ROLE ссылается на роль того же space; permission_mask=NULL, состав прав читается из текущего role_permission. Прямые grants сохраняются, поскольку их исключение не согласовано. SELF охватывает узел, CHILDREN — прямых детей, SUBTREE — узел и потомков. Только ALLOW; права объединяются, дочерний grant не отменяет разрешение предка. Закрытие поддерева под разрешающим предком требует отдельного решения о модели наследования.

Замена набора прав роли, revision и audit атомарны. Изменение действует на все bindings роли в её space. Архивирование необратимо, UUID не переиспользуется. Role/ACL revocation сериализуется с worker commit. Внешний отзыв membership не считается мгновенно видимым по старому токену: до реализации утверждается resolver/expiry protocol; истёкший или непроверяемый контекст запрещает публикацию, без автоматического повышения полномочий worker.

Platform permissions VIEW_SETUP/CREATE_SPACE/MANAGE_RETENTION_POLICIES/MANAGE_ROLES/READ_ROLE_CATALOG/VIEW_SERVICE_AUDIT задаются доверенной серверной политикой отдельно от файловых ролей. Чтение каталога интеграцией не даёт права произвольно утверждать membership или читать файлы. Назначение grants не допускает privilege escalation.

Роль в чужом space отклоняется; роль без binding не даёт READ; ROLE body с permissions отклоняется; архивирование отключает доступ при старом role UUID; два обновления одной revision дают один commit; SERVICE не подменяет USER/его роли; внешний membership protocol проверен для длительных jobs.

### FR-054. MVC-админка и общий application layer

MVC /admin/** управляет spaces, локальными ролями и ACL. Администратор выбирает состав фиксированных READ/WRITE/DELETE/SHARE/ADMIN, но не создаёт новую семантику permission code. Формы endpoints/credentials и CRUD подключений отсутствуют. Jobs и управление retention policies доступны через соответствующий защищённый REST, не входят в MVC.

REST и MVC используют одни application services, idempotency/CAS и авторизацию; loopback HTTP и SQL в контроллерах запрещены. Browser session требует CSRF, после успешного POST выполняется 303. Код и correlationId безопасно отображаются на ошибках.

Совпадение поведения REST/MVC; запрет подмены actor; отсутствие форм конфигурации S3/OpenSearch и выдачи secrets.

### FR-055. Первоначальная настройка без автоматического space

Пустой PostgreSQL допускает ноль spaces. S3/OpenSearch заданы YAML; до первого space retention policy создаётся контролируемым provisioning через защищённый REST. Первичный администратор имеет CREATE_SPACE из внешней серверной policy, не из ACL несуществующего root.

Администратор задаёт name, retentionPolicyId и initialAccess. Endpoint/bucket/prefix/index/credentials в команде запрещены. Backend использует общий YAML и выделяет уникальный prefix. Одна TX создаёт space/root/history/ACL/audit/index task/idempotency. Роли создаются после space, memberships назначаются снаружи.

Повтор не создаёт второй root; несовместимый binding не применяется автоматически. Проверка инфраструктуры вне длинной TX; YAML не создаёт bucket/index. Для начального USER/SERVICE обязательны READ+ADMIN и SUBTREE; остальные права выдаются явно.

Ручное первое space без bootstrap-key; отсутствие анонимного takeover; запрет передачи инфраструктурных настроек, идемпотентность и согласованность replicas.

## 11. Состояния и инварианты

| Объект | Значения |
|---|---|
| Space | ACTIVE, READ_ONLY, DISABLED |
| Node | ACTIVE, TRASHED, PURGING |
| Node markers (начальный набор) | TEST_CASE, REFERENCE, NEEDS_REVIEW; пустой набор допустим |
| File version | STAGED, AVAILABLE, RETIRED |
| Content object | RESERVED, AVAILABLE, GC_PENDING, DELETED |
| Job type | CORRECTOR, JOB_ROLLBACK, TREE_RESTORE |
| Job | QUEUED, RUNNING, CANCEL_REQUESTED, FINALIZING, COMPLETED, COMPLETED_WITH_ERRORS, CANCELLED, FAILED |
| Discovery | PENDING, RUNNING, COMPLETE, CANCELLED, FAILED |
| Item | WAITING_DEPENDENCY, PENDING, RUNNING, RETRY, SUCCEEDED, UNCHANGED, CONFLICT, FAILED, CANCELLED |
| Upload | INITIATED, UPLOADING, VERIFYING, COMPLETED, ABORTED, EXPIRED, FAILED |
| Search/GC task | PENDING, RUNNING, RETRY, DONE, FAILED |

Основной flow задания:

~~~text
QUEUED → RUNNING → FINALIZING → COMPLETED / COMPLETED_WITH_ERRORS
             ↓
      CANCEL_REQUESTED → CANCELLED

Неустранимая ошибка discovery/оркестрации → FAILED
Зависший FINALIZING восстанавливается идемпотентной повторной финализацией.
~~~

Обязательные инварианты:

1. currentVersion принадлежит тому же файлу и ссылается на доступные проверенные байты.
2. Активные siblings имеют уникальные нормализованные имена; дерево не имеет циклов. tree_path папок соответствует parent_id; у FILE всегда NULL.
3. Узлы и версии не пересекают tenant/space произвольно.
4. Retry/lease expiry не создают повторно опубликованный результат item.
5. После commit cancel новые изменения этого job не публикуются.
6. GC не удаляет удерживаемые/current/reachable bytes.
7. OpenSearch не определяет фактическое существование, ACL или состав restore.
8. COMPLETED не выводится только из приблизительных counters.
9. Ошибка или cancel job не означают отсутствие уже опубликованных изменений.
10. Tenant определяется конфигурацией, actor — доверенным identity-контекстом; произвольные заголовки не предоставляют полномочия.
11. correlationId и traceId/spanId являются диагностическими данными и не участвуют в бизнес-CAS или deduplication команды.

| Параллельные save одного файла | Один успешный commit; другой — конфликт |
| Rename папки | tree_path не меняется |
| Move папки с вложенными TRASHED папками | Все folder paths изменены одной TX; файлы не переписаны |
| Move выше maxAtomicMoveFolders | 413, parent_id и tree_path остались прежними |
| Restore после последующего move | История читается по историческим связям; current paths пересчитаны |
| Два job на пересекающихся roots | Разные файлы обрабатываются параллельно; общий файл защищён CAS |
| Изменение шаблона в середине job | Выполняется исходный immutable snapshot |
| Результат transform равен исходному | UNCHANGED, без новой версии |
| Crash discovery после commit страницы | Возобновление без дублей manifest |
| Crash worker после S3 upload | Возобновление/GC prepared object; без двойной публикации |
| Lease передан второму worker | Первый worker не может поздно выполнить commit |
| Cancel одновременно с commit | Определённый порядок; после cancel commit новых изменений нет |
| Пользователь изменил файл после корректора | JOB_ROLLBACK даёт конфликт, сохраняет пользовательское изменение |
| Restore пересекает retention boundary | Нужная история удерживается; недоступный T отклоняется до запуска |
| Удаление исходного файла после copy | Байты копии сохранены через её ссылку |
| GC одновременно с новым hold | Либо hold защищает версию, либо hold отклонён после retirement |
| OpenSearch недоступен | Изменения сохраняются; индекс догоняет после восстановления |
| Отзыв READ при stale search result | Содержимое/snippet не раскрываются |
| Два параллельных изменения markers | Один commit; другой конфликт revision, нет lost update |
| Изменение только markers | Новая metadata revision, без новой content version или S3 upload |
| Подмена X-Actor-Id внешним клиентом | Gateway удаляет клиентское значение и устанавливает identity проверенного токена |
| Прямой вызов неразрешённого сервиса | Запрос отклонён до доступа к данным |
| SERVICE указывает USER без делегирования | Запрос отклонён; права пользователя не присвоены |
| Tenant отсутствует или UUID некорректен | API/worker не запускаются |
| Tenant в запросе отличается от конфигурации | Эффективный tenant не меняется; чужие ресурсы не раскрываются |
| correlationId отсутствует / допустим / некорректен | Генерация / сохранение / HTTP 400 с новым безопасным ID |
| Повтор идемпотентной команды с другим correlationId | Возвращается прежний результат; второй job не создаётся |
| Job обработан другой replica после crash | Сохранён исходный correlationId; текущая попытка имеет собственный span |

## 13. Нерешённые вопросы

1. Case-sensitive или case-insensitive names; Unicode normalization и ограничения имён.
2. Конкретные retention values, квоты, пределы размера файла/дерева и expression budgets.
3. Асинхронные COPY/ZIP/export jobs и их artifact/manifests: добавить явную модель.
4. Требуется ли атомарность группы файлов тестового кейса для TEST_JSON.
5. Контракт retry failed subset, rebasing и связь с исходным job.
6. Включение UI/API USER_PIN, SHARE и LEGAL_HOLD в первую версию.
7. Требуются ли copy между spaces, signed public shares и исторический full-text search.
8. Семантика T: retained logical history в UTC; точный global commit snapshot нескольких узлов требует дополнительного дизайна.
9. Контракт внешнего удержания версий для тестовых прогонов/RAG/export.
10. Перечень старых S3 API, сохраняемых через adapter, и сроки отключения прямых bucket/key mutations.
11. Перечень разрешённых caller principals, схема сервисных UUID и механизм пользовательского делегирования для прямых вызовов sprut-core.

Протокол актуальности внешнего membership остаётся открытым интеграционным решением.

Новые effective-permissions/engine-catalog API, массовый retirement версий, COPY_CONTENT и upload неизвестного размера требуют согласования или дополнения REST-контракта; расширение БД не создаёт эти API автоматически.
