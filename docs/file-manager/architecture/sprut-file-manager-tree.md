# Дерево папок: parent_id и ltree

## Модель

`fs_node.parent_id` задаёт непосредственного родителя. `fs_node.tree_path` типа `ltree` хранит производный технический путь только у папок. Отдельная таблица иерархии не используется.

| Узел | parent_id | tree_path |
|---|---|---|
| Корневая папка | NULL | label(rootId) |
| Вложенная папка | ID родителя | parent.tree_path || label(id) |
| Файл | ID родительской папки | NULL |

`label(id)` — `n_` и 32 строчных шестнадцатеричных символа UUID без дефисов. Метки не содержат имён папок. Последняя метка пути папки соответствует её ID.

Корень имеет глубину 0. Глубина папки — `nlevel(tree_path)-1`, файла — `nlevel(parent.tree_path)`. Ограничение `maxDepth` относится к обоим типам узлов.

`tree_path` не является отображаемым `path` и не участвует в MinIO object key. REST/MVC не принимают и не возвращают это поле. Отображаемый путь строится из текущих имён папок в UUID-цепочке; для файла добавляется его имя.

## Ограничения и индексы

- Liquibase подключает расширение `ltree` до создания колонки и индексов. Runtime-пользователь не получает DDL-права.
- FOLDER требует непустой `tree_path`; FILE требует `tree_path IS NULL`.
- Родитель принадлежит тому же space и имеет тип FOLDER. Корень единственный в space.
- Корневой путь равен `label(id)`. Путь любой другой папки равен пути родителя с добавленной собственной меткой.
- Однострочные условия проверяются CHECK, включая непустой путь FOLDER и соответствие последней метки ID. Межстрочное соответствие родителя и пути проверяет deferred constraint trigger после INSERT/изменения parent_id или tree_path на изменённой папке и её непосредственных дочерних папках в конечном состоянии транзакции. Rename-only его не вызывает. Прямые обходные записи запрещены.

```sql
CREATE INDEX fs_node_folder_tree_gist
    ON fs_node USING gist (tree_path)
    WHERE node_type = 'FOLDER';

CREATE INDEX fs_node_active_child_id
    ON fs_node (space_id, parent_id, id)
    WHERE status = 'ACTIVE';

CREATE INDEX fs_node_folder_child_id
    ON fs_node (space_id, parent_id, id)
    WHERE node_type = 'FOLDER';
```

Индекс по `normalized_name` сохраняется для имён и обычной навигации. GIN по markers вводится при подтверждённой необходимости. GiST ускоряет проверку принадлежности поддереву, но не гарантирует стоимость запроса, пропорциональную размеру страницы.

## Чтение дерева

Непосредственные дети выбираются по `parent_id`.

Для папок принадлежность поддереву проверяется через `tree_path <@ root.tree_path`. Для файлов выполняется JOIN на непосредственную родительскую папку и проверяется `parent.tree_path <@ root.tree_path`. Собственного пути у файла нет.

Оператор `<@` включает равенство. `GET children` явно исключает сам root. Выборка TEST_CASE включает переданный root, если это папка с нужным маркером и доступом.

Предки папки определяются метками её `tree_path`; из цепочки исключается сама папка. Для файла используется вся цепочка его родительской папки. Метки преобразуются в UUID и одним запросом сопоставляются с fs_node в том же space, с сохранением порядка. Проверяются полнота цепочки, parent_id и глубина. Несовпадение считается нарушением дерева, а не частичным успешным ответом.

Resolve отображаемого пути остаётся проходом по сегментам `normalized_name` и `parent_id`. UUID-путь не используется для поиска строки `/folder/file` напрямую.

Tenant/space, состояния всех предков и ACL проверяются до выдачи metadata или bytes. Совпадение технического пути не предоставляет доступ. TRASHED/PURGING предок скрывает ACTIVE потомков в обычных API.

Обычная страница сортируется `FOLDER first, normalized_name, id`. Рекурсивная выдача использует стабильный ID-keyset. Cursor связан с режимом, scope и фильтрами. Общего snapshot между страницами нет. Переименование или перемещение между запросами может менять состав выдачи.

`pageSize` ограничивает ответ, не число проверенных кандидатов. Для чтения задаются DB timeout, ограниченные ресурсы и отмена запроса при disconnect. Нельзя повторно сортировать всё поддерево на каждой странице и считать это ограниченным обходом. Массовая подготовка прогона требует фоновой выборки и manifest; наличие ltree не добавляет такие endpoints автоматически.

## Поиск тестовых папок

Условие поиска: FOLDER, ACTIVE, прямой маркер TEST_CASE и принадлежность одному из переданных корней. EXCLUDE вычитает поддеревья. Корни нормализуются по ltree, результат дедуплицируется по ID. Скрытые предки и текущие ACL учитываются отдельно.

Поиск не требует перечисления MinIO и разбора callseq. File Manager возвращает metadata папок и файлов; определение состава теста, параметризация и выполнение принадлежат sprut-core. Для файлов внутри выбранной папки используется путь родительской папки.

Вложенные TEST_CASE требуют отдельного правила группировки в sprut-core. Сам маркер не запрещает вложенность. ltree не создаёт согласованный snapshot версий файлов на момент запуска.

## Создание и загрузка

Структурная операция берёт exclusive lock storage_space и читает актуальные parent/ACL после блокировки.

- Создание space записывает root с `tree_path=label(rootId)`.
- Создание папки выделяет ID, вычисляет путь из текущего parent и записывает его вместе с parent_id, историей, аудитом и index intent.
- FILE placeholder и NEW upload finalize записывают `tree_path=NULL`.
- Upload UPDATE не меняет структуру и tree_path.
- Загрузка дерева создаёт папки через обычный createNode. Клиентский relative path не используется как технический путь.

## Rename и move

Rename не меняет tree_path. При переименовании папки логические пути потомков и OpenSearch обновляются через SUBTREE index intent.

Move файла меняет parent_id, имя при необходимости, revision/history/audit/index intent. tree_path остаётся NULL.

Move папки выполняется следующим образом:

1. Проверить source/target и полномочия. Прочитать authorization_revision. Preflight и проверка generation используют primary PostgreSQL.
2. Вне изменяющей TX посчитать папки под старым prefix, включая source и TRASHED/PURGING потомков, не более `maxAtomicMoveFolders+1`. Если требуется, проверить максимальную глубину и длину нового logical path по всем затрагиваемым узлам. Результат preflight относится к одной generation; при её изменении расчёт повторяется.
3. В TX взять exclusive space lock, повторно проверить generation, состояния, ACL, If-Match и идемпотентность. Цель не должна совпадать с source или находиться в его поддереве.
4. Проверить глубину и коллизии. При превышении `maxAtomicMoveFolders` вернуть `413 RESOURCE_LIMIT_EXCEEDED`, не изменяя дерево. Лимит опубликован в capabilities и задаётся YAML.
5. Запомнить oldPrefix. Вычислить newPrefix из текущего target.tree_path и label(source.id).
6. Изменить parent_id источника и заменить oldPrefix на newPrefix у всех вложенных папок. Собственный suffix источника пуст; для него устанавливается newPrefix напрямую. Для потомков сохраняется suffix после oldPrefix.
7. Сохранить revision/history источника, audit, authorization_revision и SUBTREE index intent. Все изменения фиксируются одним COMMIT.

Файлы потомков не обновляются: их parent_id не меняется, tree_path остаётся NULL. Производное обновление пути вложенной папки не считается её пользовательским редактированием: revision/updated_at/node_revision не меняются. Переиндексация учитывает изменившиеся logical paths папок и файлов.

Пакеты UPDATE внутри одной TX допустимы; COMMIT между пакетами запрещён. Бесконечный перенос с блокировкой space не допускается. При превышении лимита операция отклоняется: отдельный протокол перемещения произвольно большого дерева не вводится. Снижение лимита не запрещает хранить или читать большие деревья.

## Copy, trash, restore и purge

- COPY_NODE создаёт новый ID и путь от текущего родителя назначения. Путь источника не копируется, в том числе между spaces. Родительский item завершается до дочернего.
- TRASH без смены родителя сохраняет tree_path. Восстановление из корзины в другую папку использует тот же atomic move.
- TREE_RESTORE и структурный rollback вычисляют путь из восстанавливаемого parent_id и его актуального пути. Перенос существующей папки обновляет пути всех её текущих вложенных папок одной TX и подчиняется maxAtomicMoveFolders; превышение завершает item как FAILED с RESOURCE_LIMIT_EXCEEDED без публикации изменения.
- Восстановление одного файла содержимого не меняет tree_path.
- Purge удаляет папку только после разрешения ссылок/истории и обработки её детей. Оставлять живую папку с отсутствующим parent или неверным prefix запрещено.

tree_path не хранится в node_revision. История содержит исторические parent_node_id, имена и интервалы. Состав дерева на T строится по историческим связям, а не текущим ltree; историческое восстановление может использовать рекурсивное построение manifest. Текущий индекс не заменяет temporal history.

## Миграция существующих данных

1. Подключить ltree, добавить nullable колонку.
2. При остановленных структурных writers заполнить пути от корней по parent_id. Рекурсивный CTE допустим для этой миграции.
3. Проверить циклы, отсутствующих/чужих родителей, корни, глубину, формат меток и согласованность каждого пути. Исправлять неоднозначную структуру автоматически запрещено.
4. Создать индексы, включить CHECK/constraint trigger, проверить ограничения.
5. Запустить writers, которые синхронно поддерживают tree_path. Старые writers не должны работать после включения инварианта.

При rolling deployment требуется отдельный совместимый dual-write этап. Обычный backfill одновременно со старыми структурными writers не используется.

## Проверки

- Корень, вложенная папка, файл и пустая папка получают правильные значения.
- Rename не меняет tree_path; move файла сохраняет NULL.
- Move папки обновляет весь prefix, включая вложенные TRASHED/PURGING папки; падение до COMMIT не оставляет частичного результата.
- Превышение maxAtomicMoveFolders и конкурирующее изменение generation не изменяют дерево.
- Два встречных move и конкурентное создание ребёнка не создают цикл или устаревший путь.
- COPY, restore и rollback не копируют устаревшие технические пути.
- Исторический поиск на T работает после последующих move; current ltree не используется вместо истории.
- Поиск TEST_CASE не пропускает вложенные папки из-за немаркированного предка и не раскрывает узлы под скрытым предком.
- EXPLAIN (ANALYZE, BUFFERS) и нагрузочный тест проверяют выборку по корням/markers, JOIN файлов на родителей и пагинацию на больших данных.
- На maxDepth проверяются размер UUID-путей, построение GiST и стоимость его обновлений; предел числа меток ltree не считается гарантией индексируемости любого размера пути.

Операторы и поддерживаемые индексы: [PostgreSQL ltree](https://www.postgresql.org/docs/current/ltree.html).
